# Adapter Checklist For Future TS SDKs

A checklist for anyone building a **new** TypeScript SDK on top of
`@openbox-ai/openbox-sdk-ts` (CopilotKit, a Cloudflare/edge adapter, a
LangChain-TS SDK, or anything else). These are the hard-won lessons from
building this base SDK and its first adapter — skipping any of them risks
reproducing a bug that has already been found and fixed once.

## Contract fidelity

- [ ] **Source behavior from Core + the Python base SDK, not from an existing
      TS/JS framework SDK.** OpenBox Core's HTTP API and stored wire contract
      are canonical; `openbox-sdk-python` is the hardened second source for
      base-SDK architecture and behavior. An existing TS SDK (e.g. a
      Mastra/CopilotKit integration) is a **tooling and migration reference
      only** — never copy its behavior into a new base-level SDK without
      checking it against Core/Python first. See
      [`source-of-truth.md`](source-of-truth.md).
- [ ] When two sources disagree, **record the conflict and its resolution**
      instead of silently picking one — see
      [`contract-conflict-ledger.md`](contract-conflict-ledger.md) for the
      format and the conflicts already found for this SDK.

## Byte-exact signing

- [ ] **ASCII-escape the signed body.** `JSON.stringify` alone emits raw UTF-8
      for non-ASCII characters; Python's `json.dumps(..., ensure_ascii=True)`
      escapes every code point `>= 0x80` as `\uXXXX`. The two produce
      different bytes for any accented/non-Latin/emoji payload, which means a
      different SHA-256, which means Core rejects the signature (401). Escape
      every UTF-16 code unit `>= 0x80` (this also handles surrogate pairs
      correctly, since JS regexes iterate UTF-16 code units).
- [ ] **Wrap the raw Ed25519 seed in PKCS8 DER before loading it.** Node's
      `crypto.createPrivateKey` rejects a bare 32-byte seed and a JWK
      `d`-only key. Prefix the seed with the fixed 16-byte DER header
      (`302e020100300506032b657004220420`) and load with
      `{ format: "der", type: "pkcs8" }`.
- [ ] **No trailing newline in the canonical signing string.** It is a join of
      exactly 5 fields with `\n` as the separator
      (`UPPER(METHOD)\nPATH\nTIMESTAMP\nNONCE\nBODY_SHA256_HEX`) — a
      separator, not a terminator. `PATH` includes the API version prefix
      (e.g. `/api/v1/...`), never host or query string.
- [ ] **Use a distinct signing-timestamp formatter with a `+00:00` offset,
      never `Z`.** `Date.toISOString()` (`Z` suffix, millisecond precision) is
      correct for EVENT-payload timestamps but wrong for the SIGNING
      timestamp, which needs a literal `+00:00` offset to match the
      second-source SDK byte-for-byte. Keep two separate formatters; don't let
      one drift into the other's call sites.
- [ ] **Send the exact bytes you hashed — never re-serialize the body.**
      Serialize once, hash those bytes, sign that hash, transmit those exact
      bytes verbatim. A second `JSON.stringify` pass — even of the "same"
      object — is not guaranteed byte-identical (key order, number
      formatting) and will break Core's body-hash verification.
- [ ] **Redact/truncate BEFORE signing, not after.** Redaction changes the
      hashed bytes. Redacting post-signature either ships unredacted data or
      invalidates the signature — there is no order in which "sign, then
      redact" is correct.

## Import-light root

- [ ] Keep the package **root** export limited to pure contracts/types/errors
      — nothing that transitively imports `node:crypto`, `fetch`/network,
      OpenTelemetry, or a database driver. Consumers who only need your
      shared types (e.g. a `Verdict` enum) should never pay for crypto or
      network code, and your root import must never register global patches
      or an OTel provider.
- [ ] Put every side-effectful subsystem (signing, the HTTP client, config env
      resolution, instrumentation, the runtime) behind its own subpath export,
      added to `package.json#exports` only when a real consumer needs it
      (consumer-driven, not speculative — see "API surface" below).
- [ ] Add an **import-light guard** wired into CI after the build step: import
      the *built* root (`dist/index.js`) in a clean Node process, spy on
      `Module._load` for heavy module name patterns (db drivers, the OTel
      Node SDK, ...), and diff `globalThis.fetch` and the OTel
      global-registration symbol before and after the import. A unit test
      running inside a bundler/test-runner's virtualized module graph is not
      sufficient by itself — CJS heavy drivers can slip through it; also run
      the guard as a plain `node script.mjs` invocation against the real
      built artifact.

## Cross-language parity

- [ ] **A fixture generated by another SDK only proves parity with that SDK.**
      A byte-identical golden fixture ported from `openbox-sdk-python` proves
      your TS output matches Python's — it does **not** prove either of you
      matches the actual server contract.
- [ ] **Build a real parity gate against the canonical server's own types**,
      not just another SDK's fixtures. This project's Core-parity gate is a Go
      harness that unmarshals TS-emitted wire spans into Core's actual
      `SpanData` struct (`DisallowUnknownFields`) and independently verifies
      an Ed25519 signature with Go's own `crypto/ed25519` — proving TS ≡ Core,
      not TS ≡ ported-fixture. Build the equivalent for your target
      server/language if you're porting to a new runtime. If the gate needs a
      second-language toolchain in CI (Go, in this case), make it **fail**
      when that toolchain is missing rather than silently skip — a
      parity gate that quietly no-ops is worse than no gate, because it still
      looks green.

## Fail-closed-on-auth (client AND wrapper)

- [ ] The HTTP client must throw (never fail open) on an auth/signing
      rejection (401/403), independent of whatever fail-open/fail-closed
      network policy the config exposes. Only network/outage failures may
      honor a fail-open policy.
- [ ] **The client-level fix is not sufficient on its own.** Any adapter
      wrapper sitting between the client and the framework must rethrow that
      same fail-closed error set at the pre-operation gating boundary — a
      wrapper that does `try { evaluate() } catch { return ALLOW }` silently
      re-opens the hole the client just closed. See
      [`framework-adapter-guide.md`](framework-adapter-guide.md#fail-closed-on-auth-must-be-enforced-at-the-adapter-wrapper-layer)
      for the full explanation and the exact error classes involved — this
      was found as a real, shipped bug in the first adapter built on this
      base, not a theoretical concern.
- [ ] Prefer shipping (or consuming) one composition root — this SDK's
      `OpenBoxRuntime` — that already implements the rule correctly, instead
      of letting every adapter hand-roll its own evaluate wrapper around the
      raw client.

## Strict vs. lenient parsing — pick per trust boundary

- [ ] The `evaluate` path (server → SDK verdict) can afford to be lenient: an
      unknown/new verdict string should degrade to the safest default
      (`ALLOW`) so forward compatibility doesn't require a synchronized SDK
      release for every new field-shape Core might add.
- [ ] The **human-approval** decision path is a different trust boundary and
      must be strict: an unknown/empty decision must parse to "still pending"
      (`null`), never an implicit allow. Don't reuse the lenient evaluate
      parser for approval decisions — the two boundaries need opposite
      failure directions.

## Instrumentation

- [ ] **Never rely on OpenTelemetry to block anything.** OTel spans are
      emitted post-dispatch (after the call already happened) or can swallow
      a throw depending on the exporter/processor — there is no supported way
      to make an OTel span prevent the underlying call. Preflight blocking
      requires a real wrapper around the driver call itself: patch the
      method, evaluate before calling through, throw before calling through
      on BLOCK/HALT.
- [ ] **Never make a database driver a hard (or even declared-optional-peer)
      dependency of your base SDK.** Treat each driver as something the
      *consumer* installs; `require()` it lazily, only inside your
      instrumentation-install call, and only for drivers the caller
      explicitly names (`databases: [...]` — never auto-detected from
      `require.cache`/`node_modules`). A driver the caller never asked to
      govern must never even attempt to load.
- [ ] **Document exact per-driver coverage gaps — don't let "instrumented"
      imply "fully governed."** Two gaps found in this SDK, both durable
      architecture constraints rather than bugs to "just fix":
      - `redis` (node-redis v4/v5): typed commands (`.get()`, `.set()`,
        `.hSet()`, ...) bind to an internal executor at **module load**,
        bypassing the patched `sendCommand` prototype method entirely — only
        literal `client.sendCommand([...])` calls are governed. Per-command
        prototype wrapping was evaluated and rejected (fragile,
        version-coupled, misses module namespaces like `.json`/`.ft`/`.ts`).
      - `mongodb`: only 12 named CRUD methods (`insertOne`, `insertMany`,
        `updateOne`, `updateMany`, `replaceOne`, `deleteOne`, `deleteMany`,
        `findOne`, `findOneAndUpdate`, `findOneAndDelete`,
        `findOneAndReplace`, `bulkWrite` — see
        [`instrumentation-coverage.md`](instrumentation-coverage.md)) are
        wrapped; cursors (`find()`/`aggregate()`) and `watch()` change
        streams pass through ungoverned and untelemetered.

## API surface

- [ ] Grow `package.json#exports` **consumer-driven** — add a subpath when a
      real adapter needs it, not speculatively. An unused export is a
      compatibility promise with no consumer to justify it.
- [ ] Give each `OpenBoxRuntime`-equivalent composition root **its own**
      context-store instance — never a process-wide singleton. Two runtimes
      in one process (multi-tenant hosting, or tests) must not be able to
      clobber each other's bound activities or abort/halt flags through
      shared global state.

## Two product decisions — RESOLVED (SDK owner)

Both were confirmed; recorded here so future adapters inherit the posture.

1. **`on_api_error` default posture — RESOLVED.** Default stays `fail_open` for
   network/outage failures (auth/signing 401/403 always fail closed). A third
   opt-in config value, `fail_closed_destructive`, blocks only DESTRUCTIVE ops on
   an outage — DB writes, file writes, non-idempotent HTTP (POST/PUT/PATCH/DELETE)
   — while reads/idempotent ops and lifecycle events stay available. **Adapter
   guidance:** surface this as a config option and let operators choose; do NOT
   hard-code fail-closed. See
   [`contract-conflict-ledger.md`](contract-conflict-ledger.md).
2. **`redis` typed-command blocking — RESOLVED (accepted limitation).** Coverage
   stays `sendCommand([...])`-only; typed commands (`.get()`/`.set()`) are
   documented as NOT blocked (loud install warning +
   [`instrumentation-coverage.md`](instrumentation-coverage.md)). Per-command
   wrapping is deferred (fragile, version-coupled, no consumer). A future adapter
   needing full redis blocking must revisit the interception strategy.
